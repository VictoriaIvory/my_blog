问题日志：饼图为什么一直加载不出来
上周想把之前做的投票 demo 完善一下，给结果页加个饼图。
按照做记账本小程序的经验，这种需求直接引 ECharts 就行。可这是个只有三个页面的练手项目，为了一个圆环引几十 KB 的库，有点杀鸡用牛刀。
于是去 GitHub 上看别人怎么做。纯 CSS 那档试了，conic-gradient 能出一个饼，但做不出环，中间挖空得再叠一层圆，而且扇形边界是硬切的。通用图表库那一档 star 都是几万，更没必要。往下翻，找到一个零依赖的 SVG 小库。点开源码看了看，它画环的方式很简单：一个 circle，用 stroke-dasharray 在圆周上切段。
原理既然就这几行，那就自己画。想法确实简单：一个圆环，stroke-dasharray 把圆周切成几段，每段长度就是百分比。
但来回折腾了三轮才画对，最后又栽在一行注释上。
## 一、第一版：看不出比例
代码写完了，刷新，结果页那块地方不对——圆环不是按百分比分段，完全看不出各占多少。
先怀疑 CSS 没生效。F12 打开，circle 在，属性在，类名也匹配上了。没问题啊？没招了，照着代码一行一行查吧。翻到stroke-dasharray="30 100" 这句，突然反应过来：属性名里写的是 dasharray（虚线数组），它凭什么懂百分比？我一直以为我写的是 30%。那它的单位是什么？
我搜的是「svg 圆环 百分比」。翻了几篇教程，每段都多一个我没见过的属性：pathLength="100"。这是啥啊？去MDN 上 搜了pathLength 词条，提到：stroke-dasharray, for example, will assume the start of the path being 0 and the end point the value defined in the pathLength attribute.
哦，明白了，pathLength="100" 等于告诉浏览器"这条路全长算作 100"，之后 dasharray 里的 30 就真的是 30%。单位的问题解决了。
## 二、第二版：一个颜色
pathLength 加进去，圆环出来了。但整个环是一个颜色，像没分段。我原来的写法是每个选项画一个完整的 circle，各自设 dasharray，以为它们会首尾相接拼成一个环。
实际上每个 circle 画的都是一整圈，不是一段。它们不是首尾相接，是完全重叠——后画的把前面的盖住了，而且都从同一个起点开始。
逻辑默认每一段都从路径的 0 点起画，可是我需要的是"让这一段从第 75 格开始画"。
接着找吧。SVG 描边相关的属性就那么几个：stroke-width、stroke-dasharray、stroke-dashoffset、stroke-linecap。dashoffset 这个名字直接把用途写出来了。
但它的文档读不通。原文是"从虚线图案的哪个位置开始应用"，我看完还是不知道正负号该写哪边。于是把这句话连同我的场景一起丢给 AI，让它讲人话。它给的答案是：偏移写多少，图案就从那个位置起算，想让起点是 75，就写 −75。
试了一下，对了。所以后端算出每段的长度和前缀和（前面所有段长度之和），模板里直接取负数：stroke-dasharray="{{ item.pie_len }} 100" stroke-dashoffset="-{{ item.pie_start }}"
## 三、第三版：图表怎么是横的？
两段分开了，占比也对，但整个饼是横的，起点在右边不是上边。SVG 的坐标系从 0° 起算，而 0° 在正右方。饼图要"从正上方开始"，就得整体转 90°。
.pie { transform: rotate(-90deg); }
一行就解决了。中间试过 90deg，方向反了，变成从 6 点开始，所以是负的。
到这里图是对的。
## 四、加完注释，注释跑到页面上
本来可以提交了。我想着这段 SVG 有点绕，给后来的人（其实就是几周后的自己）留个说明，就在模板里写了：
{# 纯 SVG 饼图：pathLength="100" 把圆周归一成 100 份， 于是 stroke-dasharray 可以直接写百分比 #}
刷新，页面上出现了这两行字。
第一反应是浏览器缓存。清了三次，开了无痕窗口，重启 runserver，字还在。排除了缓存，那就只能是模板。但我搜不到——"Django 模板注释显示在页面上"这种描述，搜出来的全是别的东西。我甚至不知道该用什么词去描述。
最后是把现象直接说给 AI：Django 模板里 {# #} 写了两行，为什么内容被渲染出来了。答案很简单：{# #} 只支持单行。换了行之后，从第二行开始就不再被识别成注释，被当成普通文本输出。
正确写法是 {% comment %} 和 {% endcomment %}，这个可以跨行。
## 五、最后，把数值钉死
饼图这类东西，"看着差不多"是最不可靠的判断标准。差 5% 在屏幕上根本看不出来。还是测一下吧。
所以我把具体数值写进测试：
def test_results_has_pie_chart_with_correct_segments(self): """两段应该是 75% 和 25%，第二段从 75% 处开始。""" ... self.assertContains(response, 'stroke-dasharray="75.0 100"') self.assertContains(response, 'stroke-dashoffset="-0.0"') self.assertContains(response, 'stroke-dasharray="25.0 100"') self.assertContains(response, 'stroke-dashoffset="-75.0"')
再加一条，防止注释又漏出来：
self.assertNotContains(response, "这里写的注释")
以后再动样式，只要有一个 dasharray 算错，测试立刻变红。
## 六、0 票的时候
测试写完我试了一下零票的情况。每个扇形长度都是 0，页面上就是一个全灰的空环，看着像加载失败。改成总票数为 0 时不渲染 svg，直接显示"还没有人投票"。完美！
## 回头看：
总共遇到四个问题，三个是 SVG 的，一个是 Django 模板的。技术细节记住就行，真正让我改了习惯的是第四个。
有问题，但是它不报错。dashoffset 写成正数、多行注释漏出来、0 票画个空环——这三个的共同点是：页面能打开，看着有点怪，但没有任何提示告诉你哪里错了。没有error或者warning的报错，这类错误就只能靠"我知道正确的输出应该长什么样"来发现，凭感觉找是找不到的。
所以现在凡是能写成断言的，我都写成断言，总比人眼发现不对可靠。万一一下子没发现，把有问题的项目推出去了，那就糟了。
